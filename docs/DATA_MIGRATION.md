# 数据生命周期与迁移策略

WebAnalytics 将插件代码、统计数据库和网站原始日志分开管理，使安装、升级和重装对用户保持无感。

## 基本原则

1. 插件代码位于 `/www/server/panel/plugin/WebAnalytics`，允许覆盖安装和卸载。
2. 统计数据库、采集游标和配置位于 `/www/server/webanalytics/data`；覆盖安装和升级复用，卸载时删除。
3. 网站原始日志始终只读，任何安装与迁移动作都不会修改原始日志。
4. 数据库升级与历史恢复是两套独立流程：升级只迁移已有数据库结构，不重新扫描日志。
5. 新数据库或新网站首次只恢复最近 30 天；任务中断后按已提交游标自动续跑。
6. 用户无需手动清理、触发恢复或选择迁移方式。

## 场景决策

| 场景 | 数据库处理 | 历史数据处理 |
| --- | --- | --- |
| 首次安装 | 创建新库和当前结构 | 所有网站恢复最近 30 天 |
| 同版本覆盖安装 | 复用数据库、配置和游标 | 不重复恢复，仅续跑中断任务 |
| 插件升级 | 先创建一致性备份，再原地迁移结构 | 保留已有统计，不重新恢复 |
| 普通卸载后重装 | 删除旧库后创建新库 | 从仍存在的原始日志恢复最近 30 天 |
| 新增网站 | 创建独立站点记录 | 仅该网站恢复最近 30 天 |
| 迁移失败 | 保留原数据库和迁移前备份，安装失败退出 | 不启动采集，避免写入不完整结构 |

## 为什么默认恢复 30 天

30 天覆盖产品提供的最长查询区间，同时能显著降低大日志扫描时间、安装期 CPU/IO 和数据库膨胀。恢复完成后，普通访问明细、错误明细和聚合数据分别继续遵循 7 天、30 天和 90 天的默认保留周期。

## 幂等与安全

- `schema_version` 决定是否执行结构迁移；同一结构不会重复迁移。
- `history_import` 按网站记录一次性任务状态；已完成的网站不会因安装或升级再次恢复。
- `file_cursors` 与每批统计写入处于同一事务；异常退出后从最后一次成功提交的位置续跑。
- 结构升级前使用 SQLite Backup API 创建包含 WAL 数据的一致性备份，最多保留最近三份。
- 高于当前程序支持版本的数据库会拒绝打开，防止旧程序破坏新结构。

卸载表示删除插件及其统计数据库和配置；网站原始日志仍由 Web 服务及系统日志轮转策略管理。覆盖安装和升级不会进入卸载流程，因此会保留数据库并自动完成结构迁移。

## 恢复性能策略

- 根据日志修改时间先排除明确早于 30 天窗口的轮转文件，再按记录时间执行精确过滤。
- 大批日志自动使用 2～4 个独立进程并行解析，主恢复流程作为唯一写入者批量落库。
- 历史恢复每批最多处理 5 万行，使用批量 UPSERT 降低 SQLite 提交和索引维护开销。
- URI、客户端、蜘蛛和匿名指纹采用批内缓存，避免对重复值反复执行正则与哈希。
- 最近 7 天保留普通访问明细，最近 30 天保留错误明细；30 天范围内的聚合统计全部导入。
- SQLite 使用 WAL、内存临时表、32 MB 页面缓存和只读内存映射提升批量读写效率。
- 恢复完成后自动执行查询规划优化和温和的 WAL checkpoint。

系统不会让多个线程直接并发写 SQLite。Python 文本解析受 GIL 影响，因此使用多进程承担纯解析工作；SQLite 写入仍保持顺序批量提交，以避免磁盘争用和 `database is locked`。
